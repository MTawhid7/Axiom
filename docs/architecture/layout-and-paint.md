## Summary

- **The layout unit is fixed-point,** 1/64 of a CSS pixel in an `i32`, as in Blink, WebKit and Ladybird. Integer arithmetic is exact, so cached fragments compare exactly and an incremental layout equals a full one bit for bit (LY1). Algorithms work in logical coordinates; fragments store physical ones (LY2).
- **Boxes are generated as CSS Display specifies,** from the flat tree and computed styles, in a per-document arena, and rebuilt only where box-affecting values changed (LY3–LY5).
- **Every layout algorithm has LayoutNG's contract:** a box, a constraint space and a break token in, an immutable fragment out, and nothing else read. That is what makes fragments cacheable by constraint space (LY6). Block, inline (with text's shaping, breaking and bidi), flex, grid, positioning, fragmentation, intrinsic sizing and writing modes are Axiom's own (DP1 (b)), and **tables are marked approximate,** because neither CSS 2.1 nor CSS Tables 3 specifies automatic table layout precisely (LY7–LY15).
- **Scrolling stays with the compositor:** scroll containers become scroll nodes with their snap areas, sticky constraints and overscroll behaviour, and scrollbar thumbs are spatial nodes that the compositor moves itself (LY16–LY18).
- **Paint follows CSS 2.1's painting order** over fragments. Pre-paint builds the property trees, and display items are keyed by box identity, so unchanged boxes and stacking contexts keep their items (LY19–LY21). Content becomes PL7's primitives; paths become images in the renderer until spike S6 reports (GR5); form controls are drawn by Axiom's own theme (LY22–LY24).
- **Hit testing finishes in the renderer** over fragments and property trees; hit-test regions for the compositor are recorded during paint, as Blink records them (LY25, LY26). Geometry for script goes through IV2's synchronous entry point, and the observers run where HTML's rendering update puts them (LY27, LY28).
- **Incremental at every stage, checked against full rebuilds,** on the event-loop thread now, and ready for parallel layout over lent arenas later (LY29–LY32).

**Facts the design depends on:**
- **The painting order** (CSS 2.1, Appendix E): within a stacking context, the root's or element's background and borders, then stacking contexts with negative `z-index`, in-flow non-positioned blocks, floats, inline content, positioned descendants with `z-index: auto` or 0, then stacking contexts with positive `z-index`.
- **`display: contents`:** "The element itself does not generate any boxes, but its children and pseudo-elements still generate boxes and text sequences as normal" (CSS Display 3).
- **Tables are underspecified.** CSS 2.1's automatic table layout "reflects the behavior of several popular HTML user agents", and "UAs are not required to implement this algorithm" (§17.5.2.2). CSS Table 3 says: "This spec is not yet ready for implementation."
- **`content-visibility: auto`:** "If the element is not relevant to the user, it also skips its contents", which "must still be available as normal to user-agent features such as find-in-page, tab order navigation, etc." (CSS Containment 2).
- **Scroll snapping** constrains "the scroll positions that a scroll container's scrollport may end at after a scrolling operation has completed" (CSS Scroll Snap 1).
- **The rendering update** (HTML §8.1.7.3): animation frame callbacks run first; then, per document, style and layout run in a loop that makes `content-visibility` proximity determinations and gathers and broadcasts resize observations at increasing depth; skipped observations deliver a loop error; later, intersection observations are updated, then paint timing is marked.
- **Image dimensions:** a pair of `width` and `height` attributes "map to the aspect-ratio property" (HTML §15.2), so an image's box can be sized before the image arrives.

Read on 2026-10-19; dates in brackets are the last commits to each file, from GitHub's API.

| Engine | What the sources show |

| **Chromium** (Blink) | **`LayoutUnit`** stores "multiples of 1/64 of a pixel in an `int32_t` storage", saturating; `TextRunLayoutUnit` stores 1/65536 of a pixel in the same storage, "suitable for a run of text, but not for the whole layout space" (`layout_unit.h` [2026-04-28]). **LayoutNG:** an algorithm's input is its node and a constraint space, and "the current layout should not access any information outside this set", because fragments are cached on it; fragment offsets are "pure left/top offsets from the parent fragment"; a cached result is reused only "if the constraint space is identical", at first only without a break token; paint and hit testing traverse the fragment tree (`layout_ng.md` [2024-06-24]). **Inline layout** collects inlines with white-space processing, segments by bidi and script, shapes with font fallback, then breaks lines, builds line boxes and generates fragments (`inline/README.md` [2025-09-18]). **Paint:** pre-paint invalidates and builds the property trees; paint groups display items "into paint chunks which share the same property tree state", and reuses unchanged items and whole subsequences from the previous paint; hit-test data (wheel-event and touch-action rects, hit-test opaqueness) is recorded while painting backgrounds, for the compositor; a scrollbar is painted as a `ScrollbarDisplayItem` that the compositor can turn into a scrollbar layer (`paint/README.md` [2026-10-07]) [B1] |

**Observations** (inference):
- **Every engine read here measures CSS boxes in fixed point:** Blink, WebKit and Ladybird at 1/64 of a pixel, Firefox at 1/60, and Servo through `app_units`, whose unit is also 1/60 (background).
- **LayoutNG's contract is now common ground.** Blink's fragments, Servo's fragment tree and Ladybird's new Rust fragment tree all separate immutable layout output from the boxes; PL5 adopted the contract at Step 4.
- **Parallelism takes two shapes:** Servo parallelizes layout itself with Rayon; Ladybird keeps it sequential but moves style and layout, and paint, to one thread each, over copied-on-write render state. Axiom's PL10 keeps layout on the event loop's thread for now, and EL11's lending allows Servo's shape later without a copy (LY30).
- **The compositor owns scrollbar motion in Blink,** as it must for scrolling without the main thread; LY18 does the same with PL6's spatial nodes.

## 5. Design

### 5.1 Units and coordinates

| Rule | Decision |
|---|---|
| LY1 | **The layout unit is fixed-point:** a signed 32-bit integer counting 1/64 of a CSS pixel, with saturating arithmetic, as Blink, WebKit and Ladybird use; Firefox counts 60 app units per CSS pixel, and Servo's `app_units` crate uses the same unit (background) (§3). **Why fixed point:** integer arithmetic is exact and associative, so stored constraints compare exactly (PL5), and an incremental layout gives bit-identical fragments to a full one, whatever order sums are taken in (IV14). It costs four bytes, like an `f32`. **The range** is ±2^25 CSS pixels, about 33.5 million; results beyond it saturate. **Text runs** use 1/65536 of a pixel internally, as Blink's `TextRunLayoutUnit` does, and round to the layout unit at run boundaries. Computed lengths arrive as floating-point CSS pixels (ST4) and are converted once. **Paint** converts to floating-point device pixels, snapping box edges to device pixels so that borders and backgrounds stay sharp. This answers the rendering pipeline's open question 4 |
| LY2 | **Logical in algorithms, physical in fragments.** Algorithms work in logical coordinates (the inline and block axes, from `writing-mode` and `direction`, LY14). Fragments store physical sizes and offsets relative to their parent fragment, as LayoutNG's do (§3). So pre-paint, paint and hit testing never handle writing modes; pre-paint maps fragment offsets into the property trees' spaces (LY19) |

### 5.2 Boxes

| Rule | Decision |
|---|---|
| LY3 | **Boxes are generated as CSS Display specifies** (PL4), from the flat tree (HD24) and computed styles (ST15): outer and inner display types; nothing for `display: none`; no box of its own for `display: contents`; boxes for pseudo-elements (ST18) among the element's children; **anonymous boxes** where CSS requires them, such as block wrappers for inline content beside blocks, table wrappers and missing table parts, and flex and grid items around text; blockification of flex and grid items, floats and positioned boxes. **Each box records** its DOM node's identity (index and generation, HD11) and pseudo-element kind, a reference to its computed style, and its kind's data. Boxes live in a per-document arena outside the heap (PL1, PL4) |
| LY4 | **The box tree is rebuilt only where needed** (IV4). ST20's box-tree changes, and HD15's insertions and removals, mark the nearest box whose children changed; construction reruns for those children, reusing unchanged child boxes. A change of a box's kind, such as its `display`, rebuilds its subtree. Text nodes become items of their inline formatting context, and a text change re-collects that context's items (LY8) |
| LY5 | **Replaced elements and child frames.**<br>• **Images** are sized from the dimensions and orientation the decoder reports before any pixels (IM4, IM9). Their `width` and `height` attributes map to `aspect-ratio` (HTML §15.2), so the box doesn't move when the image arrives. `object-fit` and `object-position` place the image in its box.<br>• **Video and canvas** are replaced boxes whose content is a layer or a shared resource (GR10).<br>• **`iframe`, `embed` and `object`** with a child frame are replaced boxes that carry the frame's token (FT3). Their rectangles go to the browser with the display list, and the child receives its viewport from the browser (IV13).<br>• **SVG roots** (LY23) and **form controls** (LY24) |

### 5.3 Layout

| Rule | Decision |
|---|---|
| LY6 | **One contract for every algorithm.** An algorithm is a function of a box (its style and children), a **constraint space** (available sizes, percentage bases, which sizes are fixed, the float exclusions and block offset of its formatting context, and the fragmentation state) and a **break token** saying where to resume. It returns a layout result: an immutable fragment (PL5), with its out-of-flow descendants and margin-collapsing state. **It reads nothing else,** as LayoutNG requires, because caching depends on it (§3). **Caching** (IV5): each box keeps its latest results, keyed by constraint space; a clean box offered an equal constraint space returns its fragment without visiting its descendants. Dirtiness comes from ST20's flags and propagates up only to the nearest layout boundary: containment, or a scroll container whose size doesn't depend on its content (IV5, LY15). ST25's nested lifecycles for size containers, proposed as an amendment to ADR-0007 for Gate C, run inside this contract, with the container's size as their input |
| LY7 | **Block layout:** block formatting contexts; margin collapsing as CSS 2.1 §8.3.1 specifies, including margins that collapse before the formatting context's block offset is known; floats and clearance, through an exclusion space carried in the constraint space; and `display: flow-root` and the other boxes that establish block formatting contexts |
| LY8 | **Inline layout and text,** in LayoutNG's phases (§3), through text's interface (§6):<br>1. **Collect** an inline formatting context's items and text, in PL11's form, applying CSS Text's white-space processing and `text-transform` (ICU4X's case mapping, TX1).<br>2. **Itemize** by bidi level (TX17), script, font (TX6's fallback) and language.<br>3. **Shape** runs (TX9, TX11), with the shaped-word cache (TX10).<br>4. **Break lines** at TX16's opportunities, under `white-space`, `overflow-wrap`, `word-break`, `line-break`, `hyphens` (TX18) and `text-wrap: balance \| pretty` (CSS Text 4). A line edge is reshaped only where HarfRust marks breaking unsafe, the use its `UNSAFE_TO_BREAK` flag documents (§3).<br>5. **Build line boxes:** inline boxes and atomic inlines, baseline alignment and `vertical-align`, `line-height` (CSS Inline 3), `text-align` and justification, `text-indent`, then bidi reordering per line (TX17).<br>6. **Generate** line fragments holding glyph runs (font, size, glyph IDs, advances and offsets, and their text range), which paint turns into atlas entries (TX13, TX14).<br>Collected items and shaping results are kept per formatting context, so a change that affects only paint shapes nothing again (inference) |
| LY9 | **Flexbox and grid** follow CSS Flexible Box Layout 1 and CSS Grid Layout 1 and 2, including subgrid, as Axiom's own code (DP1 (b)), with intrinsic sizes and percentages as CSS Box Sizing 3 specifies. Grid lanes (CSS Grid 3) and gap decorations (CSS Gaps 1) are staged. Servo lays out grid through Taffy (§3); for Axiom, Taffy is a candidate differential oracle (LY32), not a dependency |
| LY10 | **Tables are approximate** (§2). Automatic table layout follows the engines where they agree, as WPT's `css/css-tables` measures, and CSS Table 3's draft elsewhere; its code and tests are marked approximate, as `execCommand` is (HD28). Fixed table layout, the table box structure (wrappers and anonymous parts) and `border-collapse` follow CSS 2.1 as written |
| LY11 | **Positioning** (CSS Positioned Layout 3): relative, absolute and fixed boxes. Out-of-flow boxes are laid out by their containing block after its in-flow content, from static positions recorded during in-flow layout. **Sticky boxes:** layout computes the sticky view rectangle and the containing block's limits, and sends them as a sticky spatial node (PL6), so the compositor moves the box during scrolling (IV8). **The top layer** (dialogs, popovers, fullscreen; HD29) paints above the root stacking context (CSS Positioned Layout 4). **Anchor positioning** (CSS Anchor Positioning 1) is staged; it resolves anchors during the containing block's layout, with position fallbacks |
| LY12 | **Fragmentation through break tokens.** An algorithm that runs out of space in a fragmentainer (a column or a page) returns a fragment and a break token, from which the next fragmentainer resumes, as LayoutNG's block fragmentation does (§3). Multi-column layout, pages (CSS Paged Media 3), `break-*` properties, orphans and widows, and monolithic content follow CSS Fragmentation 3. Caching starts with unfragmented results, as LayoutNG's did (§3). **Printing** lays out pages this way; how printed pages reach a PDF without font parsing in the browser is decided at the printing milestone (§10, item 1) |
| LY13 | **Intrinsic sizes** (CSS Box Sizing 3): min-content and max-content contributions are computed by the same algorithms run with an intrinsic constraint space, cached per box beside its layout results, and invalidated with them. `fit-content`, `stretch`, `aspect-ratio` and `contain-intrinsic-size` follow CSS Box Sizing 3 and 4 and CSS Containment 2 |
| LY14 | **Writing modes:** horizontal and vertical writing modes, `text-orientation` and `text-combine-upright` (CSS Writing Modes 4); orthogonal flows, whose available sizes are resolved as that specification says; logical properties (CSS Logical Properties 1), mapped by style at computed-value time. Vertical text takes its orientation from ICU4X's data (TX1), and is shaped through text's interface (TX9) |
| LY15 | **Containment and `content-visibility`** (CSS Containment 2). Layout and size containment make layout boundaries (IV5); paint containment makes paint boundaries. `content-visibility: hidden` skips a subtree's contents; `auto` skips them while the element isn't relevant to the user, as determined in the rendering update's loop (LY28), and the skipped contents stay available to find-in-page, tab order and selection, as specified (IV11) |

### 5.4 Scrolling

| Rule | Decision |
|---|---|
| LY16 | **Scroll containers are scroll nodes** (PL15, IV8). Each scroll container (CSS Overflow 3) becomes a scroll node with its scrollport, its scrollable overflow rectangle and its contents' property-tree state. Its offset follows IV8's two copies, reconciled by sequence numbers. `scrollbar-gutter` reserves space for classic scrollbars; overlay scrollbars take none (LY18) |
| LY17 | **Snapping, anchoring and overscroll travel with the scroll node.**<br>• **Snapping** (CSS Scroll Snap 1): layout computes snap areas and alignments and sends them with the scroll node, so the compositor picks the snap position when a user scroll ends, without the renderer (IV8). Script scrolls snap in the renderer.<br>• **Anchoring** (CSS Scroll Anchoring 1): after layout, the renderer adjusts a scroll offset to keep the anchor node in place, a renderer-originated scroll that IV8 reconciles.<br>• **`overscroll-behavior`** goes to the compositor for scroll chaining (IN4).<br>These are data on PL6's scroll nodes, not new item kinds |
| LY18 | **Scrollbars move with the compositor.** Overlay or classic scrollbars follow the system setting, which the browser sends with the environment (ST23). A thumb is a spatial node whose position is a function of its scroll node's offset, so the compositor moves it during user scrolling without a renderer frame, and fades overlay scrollbars on its own clock (EL22). Thumbs and tracks are drawn as rounded rectangles (GR3), styled by `scrollbar-color` and `scrollbar-width`. Blink similarly hands scrollbars to its compositor (§3). **No amendment is needed** (SC1): a thumb uses PL6's spatial nodes, as sticky positioning does, and PL7's rounded rectangles |

### 5.5 Paint

| Rule | Decision |
|---|---|
| LY19 | **Pre-paint builds the property trees** (PL6), walking fragments in containing-block order:<br>• **spatial nodes:** transforms, `perspective`, scroll frames, sticky and fixed positions, scrollbar thumbs;<br>• **clip nodes:** overflow clips, rounded corners, `clip`, `clip-path`;<br>• **effect nodes:** opacity, filters, `backdrop-filter`, blend modes, `isolation`, masks.<br>It records each fragment's property-tree state. **Incrementally** (IV6), a transform, opacity or filter change updates its node only (ST20's composite-only class). **3D rendering contexts** (`transform-style: preserve-3d`) are staged; their depth sorting is designed with the compositor at that milestone (§10, item 2) |
| LY20 | **Painting order is CSS 2.1's Appendix E** (§2), with later modules' additions: flex and grid items paint like inline blocks and honour `z-index`; the top layer paints above the root stacking context; and the properties that create stacking contexts in later modules (opacity below 1, transforms, filters, `isolation`, `contain: paint`, `will-change` and the rest) create them. **Paint walks fragments, not boxes,** so a fragmented box paints once per fragment, as in LayoutNG (§3) |
| LY21 | **Display items are reused by identity** (IV6, PL14). An item's ID is its box's identity (node index and generation, and pseudo-element kind) with the item's kind and index within that box. Items are grouped into chunks by property-tree state (PL6). A box whose fragment and style didn't change keeps its items, and a stacking context whose contents didn't change is reused whole, as Blink's subsequence caching does (§3). Only changes go to the compositor (PL14) |
| LY22 | **Content becomes PL7's primitives:**<br>• **backgrounds:** colours, images and gradients, with CSS Backgrounds' repeat, size, position, origin and clip, as GR3's rectangles, images and gradients;<br>• **borders:** solid borders with any radii as GR3's simple borders; other styles (dashed, dotted, double, groove, ridge, inset, outset) and CSS Borders 4's corner shapes as path images (GR5);<br>• **box shadows** as GR3's shadows; outlines and focus rings;<br>• **text:** glyph runs as atlas entries (TX13, TX14); decorations and emphasis marks as rectangles or paths; `text-shadow` as glyph items under a blur effect;<br>• **images** as decoded resources at their displayed size (IM5), with `image-rendering`;<br>• **canvas and video** as resources and layers (GR10) |
| LY23 | **SVG, clip paths, masks and filters.** SVG content follows SVG 2's own layout: viewports, `viewBox` and `preserveAspectRatio`, `use` instances, markers, and text through text's interface. **Its paths are filled and stroked by the renderer's Rust rasterizer into image resources,** as GR5 decides, at least until the graphics milestone, to which the owner deferred GR5's amendment (OQ-24). So are `clip-path` shapes other than rectangles and rounded rectangles, CSS masks and SVG filters; CSS filter functions run on the compositor's filter pipelines (GR3). Path images are cached per document by path, style and scale, and rasterized again when the scale changes. Hit testing uses the same path code (LY25) |
| LY24 | **Form controls are painted by Axiom** (HD27), with a theme of Axiom's own that draws macOS-like controls from rectangles, paths and text, with no AppKit in the renderer. It follows the accent colour, dark mode and increased contrast that the environment reports (ST23, AX10); base appearance follows its user-agent rules (ST12). The theme's metrics are fixed at implementation and checked by reference tests |

### 5.6 Queries and observers

| Rule | Decision |
|---|---|
| LY25 | **Hit testing finishes in the renderer** (IN2). For a routed event, the renderer walks fragments in reverse painting order through the property trees: inverse transforms; clips, including rounded corners and `clip-path` by point-in-path tests; the compositor's latest scroll offsets (IV8); and `pointer-events` and `visibility`, including SVG's geometric `pointer-events`. The result is a DOM node, with a text position for selection and `caretPositionFromPoint()`. The compositor routes events to child frames by token (IN1), so a renderer never hit-tests another frame's content |
| LY26 | **Hit-test regions are recorded during paint** (PL16), as Blink records hit-test data while painting backgrounds (§3): each frame's hit-testable areas with their scroll nodes; where HD20's counts show listeners that may block scrolling; and imprecise marks where a clip path or an unusual transform leaves the compositor unable to decide (IN1) |
| LY27 | **Geometry for script** (CSSOM View): the `offset*`, `client*` and `scroll*` attributes, `getBoundingClientRect()`, `getClientRects()`, `elementFromPoint()`, `elementsFromPoint()`, `caretPositionFromPoint()`, `scrollIntoView()`, `scrollTo()` and `scrollBy()` go through IV2's synchronous entry point, which runs layout for that document only. Transformed geometry is computed from fragments and computed transforms, without painting. Script scrolls are renderer-originated offsets, which win over the compositor's (IV8) |
| LY28 | **Observers run in the rendering update, as HTML orders it** (§2). For each document, style and layout run in a loop: `content-visibility: auto` determinations are made (LY15), resize observations are gathered at increasing depth and broadcast, and the loop repeats while observations remain; skipped ones deliver the loop error. Intersection observations update afterwards, from fragments and property trees. **A frame's visible rectangle in the top-level viewport arrives from the browser with its viewport** (IV13), so an IntersectionObserver in an out-of-process frame sees what an in-process one would (AC1) |

### 5.7 Threads, memory and tests

| Rule | Decision |
|---|---|
| LY29 | **Incremental at every stage, and checked** (SC7): the box tree (LY4, IV4), fragments (LY6, IV5), property trees (LY19, IV6), display items (LY21, IV6) and damage (IV7). IV14's test mode rebuilds boxes, fragments and the display list from scratch after each update and compares; fixed-point arithmetic makes the comparison exact (LY1) |
| LY30 | **Threads** (PL10). Box construction, layout, pre-paint and paint run on the document's event-loop thread. Glyph and path rasterization and image decoding run on the helper pool (TX19, GR5, IM1); encoding the display-list update may use a helper (PL10). **Parallel layout, later:** independent formatting contexts can be laid out on the helper pool from DOM arenas and box trees lent read-only (EL11), as Servo uses Rayon in layout (§3); built only when profiling justifies it (PL10). Ladybird instead runs style and layout on a thread of their own, over copied-on-write render state (§3); lending gives Axiom parallelism without that copy (§9, alternative E) |
| LY31 | **Memory has owners** (PL13). Box and fragment arenas belong to their document. Successive fragment trees share unchanged fragments, which are freed when no tree refers to them. Display lists are bounded per frame; path images and glyph atlases belong to the renderer and are evictable (TX21). **Estimates** (inference): under 100 bytes per box and per fragment, plus kind data and text, keeps a 10,000-element page's box and fragment trees near 2 MB. Step 6 measures them against B3's 50 MB per renderer |
| LY32 | **Deterministic, headless and tested** (SC8). Layout depends only on its inputs; fixed-point arithmetic is exact (LY1); system fonts are an input, so pixel tests use web fonts (TX21). **Recursion depth is bounded** wherever the document controls it (§7). **Oracles:**<br>• WPT's layout and painting directories [T1]: `css-display`, `css-box`, `css-sizing`, `css-flexbox`, `css-grid`, `css-gaps`, `css-tables` (approximate), `css-multicol`, `css-break`, `css-position`, `css-anchor-position`, `css-overflow`, `css-scroll-snap`, `css-scroll-anchoring`, `css-contain`, `css-writing-modes`, `css-logical`, `css-inline`, `css-text`, `css-text-decor`, `css-ruby`, `css-shapes`, `css-backgrounds`, `css-borders`, `css-images`, `css-masking`, `filter-effects`, `compositing`, `css-transforms`, `css-ui`, `css-page` and `cssom-view`, and the top-level `svg`, `resize-observer` and `intersection-observer`;<br>• reference tests through the headless embedder's offscreen compositor (EM9, GR11);<br>• IV14's rebuild comparison (LY29);<br>• differential testing of flex and grid against Taffy, a candidate test tool (§10, item 3);<br>• fuzzing with generated documents, for crashes, hangs and stack depth (Step 6) |

## 7. Security

- **Paint emits only PL7's validated primitives,** which the compositor validates again before drawing (PL9): from M2 in the GPU/compositor process, at M1 in the browser (as amended in Round 1, RV1-02). Fonts and image bytes never leave the renderer (TX14, IM1).
- **Untrusted structure, bounded work.** Layout's only parsing is SVG's geometry syntax, such as path data, in safe Rust (rule 5). A hostile document can still be deep or huge: recursion depth is bounded wherever the document controls it, using explicit work stacks past a limit, and every quantity saturates instead of overflowing (LY1). Exhaustion harms only the attacker's tab, but a stack overflow would abort the renderer (inference).
- **No other frame's content is visible.** The compositor routes input by frame token (IN1), and a renderer hit-tests and measures only its own frames (LY25). A child frame learns only its own visible rectangle from the browser, the information IntersectionObserver exposes (LY28), never its parent's layout.
- **Form controls and scrollbars need no AppKit in the renderer** (LY24, HD27), as the process model requires.

## 8. Staging and the complete model

| Stage | What exists |
|---|---|
| First document milestone | The box tree; block and inline layout, with text in horizontal writing modes and bidi; floats; relative, absolute and fixed positioning; images and child frames; overflow and scroll nodes; backgrounds, solid borders, shadows and text; stacking contexts, display items and their reuse; hit testing and hit-test regions; CSSOM View's basic geometry |
| Next | Flexbox and grid; tables (approximate); multi-column layout; sticky positioning; vertical writing modes; snapping and anchoring; containment and `content-visibility`; ResizeObserver and IntersectionObserver; SVG; clip paths, masks and filters; form controls and scrollbars |
| Later | Printing and paged media; anchor positioning; grid lanes and gap decorations; ruby; `shape-outside`; 3D rendering contexts; `text-wrap: pretty`; view transitions (with CP4 and CP14); parallel layout, if profiling asks for it |

**Anchor positioning** (Round 2, [RV2-15](../review/round-2/03-findings.md#rv2-15-style-hooks-from-interop-2026)), staged "Later" above, needs style during layout: each position option is tried by style's nested lifecycle for one element (ST25), within its parent's layout. When a corpus page or a milestone's selection needs it, it is built that way.

**The complete model** (SC9): every script and writing mode goes through text's interface and LY14's logical coordinates; a new formatting context is another algorithm under LY6's contract; a new paint effect is an effect node or a primitive; a new scrolling feature is data on the scroll node; parallel layout stays possible behind LY30.

## 9. Alternatives considered

| | Alternative | Assessment |
|---|---|---|
| A | **Taffy** for flexbox, grid and block, as Servo uses it for grid | DP1 (b) makes layout core, and Axiom's algorithms must share one contract (LY6), unit (LY1) and box arena. Rejected as a dependency; a candidate differential oracle (LY32) |
| B | **Floating-point layout units** | Simpler, with more range, but floating-point sums depend on their order, so an incremental layout could differ in its last bits from a full one, and cache keys would compare inexactly. The engines read here all measure CSS boxes in fixed point (§3). Rejected (LY1) |
| C | **1/60 of a pixel,** as Firefox and Servo count | It represents thirds exactly, but 1/64 matches three engines and converts by shifts. Rejected narrowly |
| D | **Painting scrollbars in the renderer** like other content | A thumb would lag during compositor-driven scrolling, until the next renderer frame. Rejected (LY18) |
| E | **Style and layout on a thread of their own,** over a copied render state, as Ladybird now does | It frees the event loop during long layouts, but copies DOM-derived state each update, which the rendering pipeline's alternative C rejected. Input and scrolling already bypass the event loop (IV8, IN1). Rejected for now; profiling may revisit it |
| F | **Native form controls** through AppKit | AppKit isn't available in the renderer (HD27). Rejected |
