## Summary

- **The CSS parser is Axiom's own** (DP1 (a)): CSS Syntax 3's tokenizer and parser, generic over PL11's 8-bit and 16-bit code units, so stylesheets from the DOM and from script are never converted to UTF-8 (ST1). Fetched stylesheets are decoded as CSS Syntax specifies, by TX3's decoders, and parsed on the helper pool (ST2, ST33). **Every property is defined once,** in a table from which the build generates parsers, computed-value storage, invalidation impact and the CSSOM's accessors (ST3).
- **Selectors match right to left over the DOM's columns,** lent read-only (PL2): rules are bucketed by their rightmost compound, descendant combinators are filtered by a counting Bloom filter of ancestors, and `:has()` has its own invalidation (ST7–ST10). Matching writes nothing into the DOM. **No selector is compiled to machine code:** WebKit's selector JIT would need dynamic code generation, which every renderer profile but `renderer-jit`'s denies (ST11, J3).
- **The cascade follows CSS Cascade 5 and 6:** origins and importance, shadow-tree context, the `style` attribute, layers, specificity, `@scope` proximity and order (ST12). Custom properties are substituted at computed-value time, with cycle detection and the expansion limit the specification requires (ST13).
- **Computed styles are immutable and shared** (PL3): grouped into reference-counted structs that an element shares with its parent or the initial style when unchanged, deduplicated through a rule tree, a style sharing cache and a cascade cache (ST14–ST17). The caches are acceleration only: budgeted, evictable under memory pressure, and never needed for a correct answer (ST17, ST34).
- **Invalidation, IV3's details:** invalidation sets built from every selector's features, fed by HD15's mutation hook, pending until style is needed; restyling stops where inherited values didn't change; each change is classified by what it dirties next (ST19–ST22).
- **Container queries are resolved during layout:** layout restyles a size container's subtree once the container's size is known, as Blink does. That nests a lifecycle inside layout, **an amendment to ADR-0007's IV1 the owner accepted** at Gate C, with a correction to IV2's examples: some `getComputedStyle` reads need layout (ST25, ST31).
- **Animations and transitions run on Web Animations' model,** timed by EL22's frame times. Those GR9 allows run on the compositor from a description, with the renderer keeping the authoritative timing model (ST27–ST29).
- **The CSSOM is a view over immutable stylesheet contents,** edited by copying only the path to the change, so contents can be shared between documents, lent to helper threads, and diffed for invalidation (ST30).
- **`:visited` uses partitioned history,** as Selectors 4's Appendix C describes: the browser keeps the history, and a renderer learns only what its own origin could have observed (ST10, §7).

**Facts the design depends on:**
- **Preprocessing replaces lone surrogates.** CSS Syntax §3.3 replaces "any U+0000 NULL or surrogate code points" with U+FFFD, noting that the only way to produce one "is by directly assigning a DOMString with one in it via an OM operation".
- **Decoding** (CSS Syntax §3.2) takes the protocol's charset label first, then `@charset` within the first 1,024 bytes (a declared UTF-16 becomes UTF-8), then the referring document's environment encoding, then UTF-8. The decode algorithm lets a byte-order mark override all of them.
- **The cascade's order** (Cascade 5 §6.1, Cascade 6): origin and importance (transitions; important user agent, user and author; animations; normal author, user and user agent), context, element-attached styles, layers, specificity, scope proximity (level 6), order of appearance. For context, "for normal rules the declaration from the outer context wins, and for important rules the declaration from the inner context wins", in shadow-including tree order. Presentational hints enter as user-agent rules or in "a special-purpose author presentational hint origin between the regular user origin and the author origin" (§6.5).
- **Custom properties:** "If there is a cycle in the dependency graph, all the custom properties in the cycle are invalid at computed-value time." Against "a variation of the 'billion laughs attack'", user agents "must impose a UA-defined limit on the allowed length of the token stream that a `var()` function expands into" (Custom Properties §3.3).
- **Selectors:** `:has()` "cannot be nested"; in quirks mode, class names and IDs "must be matched ASCII case-insensitively". `:visited` "comes with obvious privacy implications", and Appendix C describes partitioned history, keyed by the visited URL, the origin that started the navigation and its top-level site, with which `:visited` "can be treated as a normal pseudo-class".
- **CSSOM:** `getComputedStyle` returns resolved values, which for `width`, `height`, the margins and paddings (and the insets of positioned elements) are **used values** unless the element's `display` resolves to `none` or `contents` (§9). A cross-origin sheet's `cssRules` throws when its origin-clean flag is unset; `replace()` drops `@import` rules from constructed sheets.
- **Container queries:** `container-type` is `normal | [ [ size | inline-size ] || scroll-state ]`; every element is a query container for style queries.
- **HTML:** a linked stylesheet whose `Content-Type` isn't `text/css` isn't applied, except in a quirks-mode document for a same-origin resource.

**Observations** (inference):
- **The three mature engines cache the cascade by what matched:** Stylo through its rule tree, Blink and WebKit through a hash of the matched declarations. Blink's cached styles hold shared "substructures", and WebKit's styles are `DataRef` groups. Axiom's PL3 takes the same direction (ST14–ST17).
- **Selector matching doesn't need code generation.** Blink's and Stylo's matchers walk selector data structures (background), and Ladybird evaluates its compiled IR; only WebKit generates machine code, which J3 forbids in Axiom's renderers.
- **Stylo shows what parallel style costs without lending:** element data behind `AtomicRefCell`, and `unsafe` to send nodes between threads. Axiom's lendable arenas (PL2) allow the same traversal in safe Rust (ST33).
- **Ladybird's new engine, in Rust and only two months in production, treats memory as a primary constraint,** which Axiom shares (G4). Two of its principles transfer directly: acceleration state that can be evicted at any time without changing a result, and a cache-free path that defines correctness (ST17, ST22).
- **Container queries break the strict order of phases in every engine that ships them:** Blink restyles during layout, and Ladybird runs extra style passes. Axiom has to make that interleaving explicit in IV1's compiler-checked lifecycle (ST25).

## 5. Design

### 5.1 Parsing and values

| Rule | Decision |
|---|---|
| ST1 | **The parser is Axiom's own,** a direct implementation of CSS Syntax 3: the tokenizer, the parser's entry points (a stylesheet and its contents, a block's contents, a rule, a declaration, component values) and nesting, where a block's leading declarations go to the rule and later ones become nested declarations rules. It is **generic over the code unit,** monomorphized for PL11's 8-bit and 16-bit forms, so `<style>` text, `style` attributes and CSSOM strings are parsed where they lie, without conversion. Preprocessing follows §3.3, including replacing lone surrogates from script. Tokens are ranges into the input; names become atoms (ST32); a token is copied only when it contains escapes. **Tokenization never fails**; errors recover as specified and are recorded for developer tools, never shown to users. Safe Rust, with no `unsafe` (rule 5). **Nesting depth is bounded** for blocks, functions, `calc()` and nested rules, so hostile input can't exhaust the stack (§7) |
| ST2 | **Stylesheet bytes are decoded as CSS Syntax §3.2 specifies:** a byte-order mark; the transport's `charset`; `@charset` within the first 1,024 bytes, with a declared UTF-16 read as UTF-8; the referring document's environment encoding; then UTF-8. **TX3's decoders** write PL11's 8-bit or 16-bit text directly (TX4), as HD3 does for HTML. A linked sheet whose `Content-Type` isn't `text/css` is not applied, except for a same-origin resource in a quirks-mode document, as HTML specifies. Bytes come through the document's loader endpoint (FT11), after ORB has run in the network process (NW12) |
| ST3 | **Every property is defined once, in a table.** Each longhand and shorthand records its name and aliases (including the Compatibility Standard's `-webkit-` aliases and mappings), its grammar, initial value, inheritance, the elements it applies to, its computed-value type, its animation type, its logical-property group, and **its impact class** (ST20). **The build generates** from it: the property identifiers and their atoms; the parsers' dispatch; the computed-style groups and their fields (ST15); the impact table; and the CSSOM's accessors for CP17 (the dashed and camel-case attributes of `CSSStyleProperties`). Blink generates its `ComputedStyleBase` the same way (§3) |
| ST4 | **Each value stage is a type.** Declared values parse into typed specified values; a declaration containing `var()` stays a token sequence until substitution (ST13). Computed values are typed fields: lengths absolutized to CSS pixels in floating point, percentages kept where the property says so, colours resolved but `currentcolor` kept. **Used values belong to layout** (CP15), which converts lengths to its own unit (PL5), and are never stored in computed styles. Resolved values exist only for the CSSOM (ST31). Because the stages are distinct types, a computed-value-time operation can't receive a specified value. **The hook for `zoom`** (Round 2, [RV2-15](../review/round-2/03-findings.md#rv2-15-style-hooks-from-interop-2026)): CSS Viewport's effective zoom, "the product of its computed value of zoom and all flat tree ancestors' computed values of zoom", is an inherited factor computed here, and lengths scale by it, so it affects layout as transforms don't [W2] |
| ST5 | **Math functions** (`calc()`, `min()`, `max()`, `clamp()`, and the rest of Values 4) are parsed into expression trees, simplified at parse time as far as their units allow, and finished at computed-value or used-value time as the specification orders, with its rules for infinities, NaN and range clamping |
| ST6 | **Compatibility and quirks are kept apart.** The Compatibility Standard's aliases, mappings and `-webkit-` functions are entries in the property table (ST3). The Quirks Mode Standard's CSS quirks (hashless colours, unitless lengths, and the rest) apply only to documents in quirks mode, behind one flag the parser and matcher receive. Both are standards, and implemented as written |

### 5.2 Selectors and matching

| Rule | Decision |
|---|---|
| ST7 | **Selectors parse into a compact form:** each complex selector stored right to left as compounds of simple selectors, with names as atoms and **specificity computed once** (Selectors 4 §15), including the special cases of `:is()`, `:not()`, `:has()` and `:nth-child(… of S)`, and `:where()` at zero. A nested rule's `&` takes its parent's selectors with `:is()`'s specificity (Nesting 1); `@scope` follows Cascade 6. Shadow DOM's selectors (`:host`, `:host()`, `:host-context()`, `::slotted()`, `::part()`) follow CSS Scoping and Shadow Parts |
| ST8 | **Matching reads the DOM's own columns,** borrowed read-only (PL2): the local name and namespace class, the ID and class atoms, and attributes (HD10, HD12). In quirks mode, IDs and classes compare ASCII case-insensitively, through each atom's folded form (ST32). **Element states** (`:hover`, `:focus`, `:active`, `:checked`, `:open`, `:popover-open`, `:modal`, `:user-invalid` and the rest) are DOM state bits that the event loop sets. **Matching writes nothing into the DOM:** the flags it records, such as "children affected by `:nth-child`" or "affected by `:has()`", go in style's side table (PL2). Firefox keeps such flags on the node, in a cell ([HTML and the DOM](html-and-dom.md) §3) |
| ST9 | **Rules are bucketed, and ancestors filtered.** Each rule goes in one bucket, by its rightmost compound's most selective feature: ID, class, local name or attribute name, with buckets for `:root`, rare pseudo-classes and the rest, as Stylo's `SelectorMap` does (§3). An element collects candidates from the buckets of its ID, classes, local name and attributes, and matches each right to left. **Descendant combinators** first consult a counting Bloom filter of the ancestors' local names, IDs, classes and attribute names, kept during the traversal (pushed on descent, popped on ascent), which rejects most failing matches without walking up the tree. That is the "standard optimization" Stylo, Gecko, Blink and WebKit share (§3). Each selector precomputes the hashes of its ancestor compounds |
| ST10 | **Pseudo-classes with their own costs.**<br>• **`:has()`** anchors relative selectors on the subject. Results are cached per element and selector during one style pass. A mutation invalidates only elements marked as anchors whose answer could change, walking up from the mutation to ancestors, the parent, previous siblings or ancestors' previous siblings, the four dependency kinds Stylo records (§3). `:has()` can't nest.<br>• **`:visited`** matches only links whose visit the document's own origin could have observed, by Selectors 4's Appendix C. **The browser keeps the visited history** as triples (URL, the initiating origin, its top-level site), recorded as it drives navigations (FT7). A renderer receives fingerprints of visited URLs only for the (origin, top-level site) pairs of the documents it hosts, which the browser knows from its frame tree, with updates as those partitions gain entries. With partitioning, `:visited` styles and `getComputedStyle` need no restrictions, as Appendix C notes. Until the history service exists, `:visited` never matches, the first of the specification's suggested methods. **Approved by the owner at Gate C** (2026-10-20): "Partitioned history by top-level site is approved." |
| ST11 | **Matching is interpreted, never compiled to machine code.** WebKit's selector JIT generates code at run time (§3), which J3 forbids in every renderer but `renderer-jit`. It isn't planned there either: any generated code would fall under J1's evidence rule and J7's tests, and Blink, Stylo and Ladybird show interpretation is fast enough (inference) |

### 5.3 The cascade and computed styles

| Rule | Decision |
|---|---|
| ST12 | **The cascade, in the specified order** (§2): origin and importance, context, element-attached styles, layers, specificity, scope proximity, order of appearance. **Each rule carries a precomputed key** (origin, tree context, layer order, specificity, source order); scope proximity is measured when an `@scope` rule matches. **Presentational hints:** the rules HTML §15.2 calls out as presentational hints enter "the author-level zero-specificity presentational hints part of the CSS cascade", Cascade 5's author presentational hint origin. **The user-agent stylesheet** is the rest of HTML's rendering section, form controls (HD27), and SVG's and MathML's defaults; base appearance's rules form a separate block, as Stylo flags `@appearance-base` rules (§3). It is parsed once per process and shared read-only by every document (§10, item 4). **The user origin** exists in the model, for user stylesheets and accessibility settings later. **Defaulting:** `initial`, `inherit`, `unset`, `revert`, `revert-layer` and `all`. **The hook for anchor positioning** (Round 2, RV2-15): `@position-try`'s declarations form **the position fallback origin,** "a new cascade origin that lies between the Author Origin and the Animation Origin" [W3], so it is one more value of the precomputed key's origin field; its declarations are applied during layout, as ST25 describes |
| ST13 | **Custom properties.** Computed values hold a map of custom properties, **shared by pointer with the parent** when an element declares none, and copied with changes when it declares some. `var()` is substituted at computed-value time over the dependency graph; **cycles** make their properties invalid at computed-value time; **the expansion limit** (Custom Properties §3.3) is a token count set at implementation, against WPT's `variable-exponential-blowup.html` (§10, item 5). **Registered properties** (`@property`, `CSS.registerProperty`) compute to typed values, may be non-inherited, and animate by type. `env()` reads values the browser provides |
| ST14 | **The rule tree.** The matched declarations of an element, in cascade order, form a path in a per-document tree of rule nodes, so elements that matched the same rules share one node. `!important` declarations are placed by the tree, so matching ignores importance (Stylo, §3). Rule nodes are reference-counted, hold their declaration blocks (shared with the CSSOM's contents, ST30), and are freed at the end of a style pass once unused. **A rule node is the identity of "what matched",** which the caches below compare by pointer |
| ST15 | **Computed styles are immutable, shared and grouped** (PL3). A computed style is a reference-counted value holding reference-counted **groups** of properties. Inherited groups (font, text, colour and visibility, lists, and the rest) are shared with the parent's style when unchanged; non-inherited groups (box, position, margins and padding, borders, backgrounds, effects, animation, interface) are shared with the initial style when unchanged. So a style that differs in one property allocates one group. The property table assigns groups, keeping properties that change together, and those layout reads first, side by side. WebKit's `DataRef` groups are the same design (§3). **The side table holds one reference per element** (PL3), indexed by the element's per-kind index (HD10), so text nodes cost nothing |
| ST16 | **The style sharing cache.** Before matching, an element looks among recently styled elements at its own depth. It reuses a candidate's style, skipping matching and the cascade, when they have the same parent style (by pointer), local name and namespace, classes, `style` attribute and presentational hints (by pointer), selector-visible states, and the same answers for the **revalidation selectors**: those whose result could differ between two such elements, such as attribute selectors, `:nth-child()` and sibling combinators. Stylo's measured size, 32 candidates per depth, is the starting point; Step 6 tunes it. The cache lives for one style pass |
| ST17 | **The cascade cache** holds the result of cascading a rule node, keyed by the rule node and, when the result depends on inherited values, by the parent's inherited groups (by pointer), as Blink's matched properties cache and WebKit's matched declarations cache key by what matched (§3). Elements that miss the sharing cache but match the same rules skip the cascade. **It is acceleration only:** budgeted, evicted least recently used, emptied under memory pressure (SH14), and never needed for a correct answer (ST22, ST34) |
| ST18 | **Pseudo-elements and inheritance.** Eager pseudo-elements (`::before`, `::after`, `::marker`) are styled with their element, and stored beside its style in the side table. Others (`::first-line`, `::first-letter`, `::placeholder`, `::backdrop`, `::file-selector-button`, and the highlight pseudo-elements such as `::selection` and `::highlight()`) are styled on demand by box construction and paint (CP15), and cached per document. **Inheritance follows the flat tree,** through slots (HD24), the traversal CP15's box construction shares. Subtrees under `display: none`, and those IV11 skips, are not styled in the rendering update; `getComputedStyle` styles them on demand, in a separate cache that the next mutation clears |

### 5.4 Invalidation

| Rule | Decision |
|---|---|
| ST19 | **Invalidation sets** (IV3). When a stylesheet's rules are added, every selector contributes to the scope's invalidation map: for each class, ID, attribute name and state it mentions, what a change to it invalidates (the element itself, descendants with given features, later siblings, or the whole subtree), as Blink's descendant and sibling sets do (§3). **HD15's hook reports each mutation:** an attribute change (for `class`, the classes added or removed; for `id`, the old and new atoms), a state change, an insertion or removal, or a `lang` or `dir` change. Insertions and removals also invalidate by the structural flags matching recorded (ST8): `:nth-child()`, `:empty`, `:first-child`, `:last-child` and sibling combinators. `:has()` follows ST10. **Pending, not immediate:** sets are recorded in style's side table and applied when style is next needed, by the rendering update or a query (IV2). **The hook for `attr()`** (Round 2, RV2-15): `attr()` "substitutes the value of an attribute on an element into a property" [W4], so a declaration that uses it makes its element's computed value depend on an attribute's value, which no selector need name, so the cascade records each such dependency, and HD15's hook invalidates the element when that attribute changes, as for a selector's attribute |
| ST20 | **Restyling stops early, and classifies what changed.** Recalculation visits marked elements. It compares each new style with the old one group by group, by pointer: if no inherited group changed, descendants that aren't marked keep their styles (IV3). For groups that changed, the impact table (ST3) classifies each changed property: **box tree** (`display`, `position`, `float`, `content`: IV4), **layout**, **paint**, **composite only** (the transform, opacity or filter of an element that already has its own property node: IV6), or **nothing visible**. The result goes to CP15 as per-element dirty flags |
| ST21 | **Stylesheet changes invalidate by the features of what changed.** Adding or removing a sheet or rule, or a media query result changing, applies the invalidation sets of the affected selectors to their scope (the document or one shadow tree). Changes the sets can't describe restyle the scope: layer order, `@property` registrations, `@keyframes` used by running animations, and universal selectors in sensitive positions. Bucket maps (ST9) and invalidation maps are updated per scope, incrementally where cheap |
| ST22 | **The cache-free path defines correctness.** A test mode styles every element without the sharing cache, the cascade cache, the Bloom filter or any recorded flags, and compares with the incremental, cached result by value. With IV14's rebuild of the later phases, this keeps every cache and invalidation shortcut honest. Ladybird's engine keeps such a matcher as its "correctness floor" (§3) |

### 5.5 Queries, loading and fonts

| Rule | Decision |
|---|---|
| ST23 | **Media queries** evaluate against the frame's environment, which the browser sends: the viewport (IV13), device pixel ratio, colour gamut and dynamic range, the pointer and hover capabilities of attached devices, AX10's preferences (`prefers-reduced-motion`, `prefers-contrast`, `prefers-reduced-transparency`, `prefers-color-scheme`), and the system colours and accent colour of macOS's appearance. **Each query list records the features it reads,** so a change re-evaluates only the lists that read it, and invalidates only the rules under them (IV10). `matchMedia` listeners are notified in the rendering update, as HTML orders it |
| ST24 | **`@import` and loading.** Imported sheets are fetched through the loader endpoint (FT11), resolved against the importing sheet's URL, with `layer()`, `supports()` and media conditions applied as specified, and cycles and depth bounded. **Blocking follows HTML:** an HTML document is render-blocked while it has no `body` and while stylesheets its parser created are loading, up to an implementation-defined timeout; parser-inserted scripts wait for script-blocking style sheets; the parser itself never waits for a stylesheet (IV10). Parsed contents are immutable (ST30), so one parse serves every document in the renderer that loads the same response |
| ST25 | **Container queries are resolved during layout.** Style queries need only the container's computed style, so they resolve in the ordinary pass. **Size queries** need the container's size, which is known only during layout. A size container has size containment in its contained axes, so its size doesn't depend on its descendants. During style, the subtree of a size container is **deferred** when rules in scope use size queries, or its descendants use container-relative units (`cqw`, `cqi` and the rest). When layout has sized the container, it runs **a nested lifecycle for that subtree**: style with the container's size as input, then box construction, then layout of the subtree. If a later layout pass gives the container a different size, as flex and grid sizing can, the nested lifecycle runs again. Blink does the same through `UpdateStyleAndLayoutTreeForSizeContainer` (§3). **Scroll-state queries** read scroll positions after layout, and take effect in the next rendering update.<br>**This needs an amendment to ADR-0007's IV1.** IV1 makes each phase a function whose output stays immutable for the rest of the update, with a token proving the phase finished. The output still never changes once produced; what is new is that style's output can have deferred subtrees, completed inside layout by nested phases with their own tokens. Reading the style of an element in a deferred subtree takes the nested phase's token, or `LayoutClean`. **Accepted by the owner at Gate C** (2026-10-20), with the correction to IV2's examples in ST31: "Nested lifecycle phases for size container queries are adopted." IV1 is amended in [invalidation](invalidation.md).<br>**The hook for anchor positioning's fallbacks** (Round 2, RV2-15): applying a position option means inserting its declarations "into the cascade in the position fallback origin", resolving the cascade and performing "enough layout to determine el's used styles", applied "via interleaving" [W3]. That is this rule's nested lifecycle for one element: style with the option's declarations as input, then its layout, inside the parent's layout, with IV1's amended tokens. It is built with anchor positioning |
| ST26 | **Fonts: `@font-face` is handed to text.** `@font-face` rules parse into descriptors: family, sources, `unicode-range`, weight, width and style ranges, `font-display`, feature and variation settings, and metric overrides. The document's font face set (`document.fonts`, CSS Font Loading) holds them in order, with `FontFace` objects from script. **A face loads when a text run needs it** (its `unicode-range` covers the characters), through text's loader path (TX7). Computed `font-*` values become font descriptors for TX6's matching. `font-display`'s periods are one-shot timers; a font that arrives or fails re-shapes only its text (TX20) |

### 5.6 Animations and transitions

| Rule | Decision |
|---|---|
| ST27 | **One timing model: Web Animations.** CSS animations and transitions are Web Animations objects (`CSSAnimation`, `CSSTransition`) on the document timeline, as their specifications define them. **Timeline time comes from EL22's frame times:** "update animations and send events" runs in the rendering update, at the timestamp the event loop received (Web Animations, HTML). Scroll-driven timelines read scroll offsets, which the compositor reports for user scrolling (IV8). **Animated values** form the cascade's animation and transition origins (ST12). When only animations advance, the animated groups are recomputed over the element's cached base style, without matching. **Transitions** start from style change events, comparing before-change and after-change styles (Transitions 1). When ST25's nested lifecycles restyle a subtree more than once in one update, transitions compare with the style from before the update, as Ladybird's stabilization epochs do (§3) |
| ST28 | **Which animations run on the compositor: GR9's list,** confirmed here. An animation runs there when every property it animates is in GR9's current set (first the transform family and opacity, then filter, backdrop-filter and scroll-driven timelines for them), and nothing it animates affects layout. **The renderer sends a description** with the update: the property node (PL15), keyframes with resolved values, and timing (duration, delay, iterations, direction, fill, easing including `steps()` and `linear()`, start time, playback rate). **The renderer keeps the authoritative model,** so script reading an animated value gets the same answer from the same code: the timing and easing functions live in one crate that both processes use. The renderer hears when compositor animations start and end (IV8). Percentages that depend on the box are re-resolved, and the description resent, when layout changes the box |
| ST29 | **Animation events and idleness.** Animation and transition events are dispatched from "update animations and send events". A document with running animations subscribes for frames (EL20); when none remain, and no other reason holds, it unsubscribes (IV12). Animations on the compositor need no renderer frames while they run |

### 5.7 The CSSOM and `getComputedStyle`

| Rule | Decision |
|---|---|
| ST30 | **The CSSOM is a view over immutable contents.** Parsed stylesheet contents (rules, selectors, declaration blocks) are immutable, reference-counted trees outside the heap. CSSOM objects (`CSSStyleSheet`, the `CSSRule` interfaces, `CSSStyleProperties`) are platform objects in the heap (CP16, CP17) that hold a sheet and a path into it. **An edit** (`insertRule`, `deleteRule`, `cssText`, `setProperty`) builds new versions only along the path to the edited rule, as Ladybird's program does (§3): unchanged rules keep their identity, so invalidation compares old and new rules directly (ST21). Contents can be shared by documents in the same renderer, and lent to helper threads (EL11). **The `style` attribute** is parsed when first needed (HD12) into a shared declaration block. **Constructed sheets and `adoptedStyleSheets`** follow CSSOM: a document's or shadow root's final sheets are its own, then its adopted ones, in order. **A cross-origin sheet's rules are unreadable** from script (the origin-clean flag) |
| ST31 | **`getComputedStyle` goes through IV2's synchronous entry point,** and each read runs only the phases that property needs, for that document only. **Most reads need style. Reads that resolve to used values need layout** (CSSOM §9: `width`, `height`, margins and paddings, and the insets of positioned elements, unless `display` resolves to `none` or `contents`), as Blink runs layout only for layout-dependent reads (§3). So does any read inside a deferred container subtree (ST25). IV2's rule is unchanged; **its examples were corrected by the amendment the owner accepted with ST25** at Gate C (2026-10-20) |

### 5.8 Threads, memory and tests

| Rule | Decision |
|---|---|
| ST32 | **Atoms across threads** (PL11). Property names, keywords, element and attribute names, IDs, classes, custom property names, and the names of keyframes, layers, counters and containers are atoms: static ones generated at build time, dynamic ones in the process-wide, thread-safe table. Each atom also records its ASCII-folded form, for quirks mode and case-insensitive names. **Matching only compares atoms;** atoms are created while parsing, which may run on a helper thread (ST33) |
| ST33 | **Readiness for parallel style** (PL2, PL10, EL11). The traversal is written as a function of a read-only borrow of the DOM, the stylesheets' immutable contents, and its outputs, so subtrees can later be styled on the helper pool with work stealing, as Stylo's traversal is, in safe Rust. **What exists from the start:** per-traversal Bloom filters and sharing caches; immutable inputs; a thread-safe atom table. **What is chosen when parallel style is built:** how each element's single write reaches the side table (per-task buffers merged on the event loop's thread, or per-element atomic slots), and how the rule tree accepts concurrent insertion. Built only when profiling shows that style limits frame production (PL10). **Stylesheets that arrive from the network are parsed on the helper pool now:** input and output are outside the heap (EL9) |
| ST34 | **Memory has owners and budgets.** Per document: the stylesheets' contents (shared), the bucket and invalidation maps per scope, the rule tree, and the side table. Per process: the user-agent stylesheet and the atom table. **Estimates** (inference): a side-table entry of 16 bytes per element (a style reference and flags), and computed styles shared widely enough that distinct groups are far fewer than elements; a 10,000-element page then costs about 160 KB of side table, plus its distinct styles. Step 6 measures both against B3's 50 MB per renderer. **Caches are the only discretionary memory:** the cascade cache is budgeted and evictable, the sharing cache lives for one pass, and both empty under memory pressure (SH14), as Ladybird's evictable tier does (§3) |
| ST35 | **Threads and idleness.** Style runs on the document's event-loop thread, in the rendering update or a synchronous query (PL10), and never runs script. Network stylesheets are parsed on the helper pool (ST33). Idle, style does no work: media query changes, font periods and animations arrive as events or one-shot timers, never by polling |
| ST36 | **Deterministic, and tested at boundaries.** Style output depends only on its inputs: never on cache state, traversal order or, later, thread count (ST22). Time comes from the virtual clock in tests (EL24), and the environment that ST23 reads, including system colours and fonts, is injected, so tests are stable on any Mac (SC8). **Oracles:**<br>• WPT's CSS directories [T1]: `css-syntax`, `css-values`, `css-variables`, `css-properties-values-api`, `css-cascade`, `css-nesting`, `selectors`, `css-pseudo`, `css-shadow` (scoping, with Shadow Parts in `part/`), `mediaqueries`, `css-conditional` (with `container-queries/`), `css-contain`, `css-fonts` and `css-font-loading`, `css-animations`, `css-transitions`, `cssom` and `css-view-transitions`; and the top-level `web-animations`, `scroll-animations` and `compat`;<br>• the css-parsing-tests suite for the tokenizer and parser [T2];<br>• the cache-free path against the cached one (ST22), and IV14's rebuild comparison;<br>• tests that the parser and the expansion limit survive hostile inputs, and fuzzing of the parser (Step 6) |

## 7. Security

- **Rule of 2:** the CSS parser, the selector parser and the property parsers handle untrusted input inside the sandboxed renderer, in safe Rust with no `unsafe` (rule 5, SC2, SC3).
- **Bounded work:** the `var()` expansion limit that Custom Properties §3.3 requires (ST13); bounded nesting depth in the parser (ST1); bounded `@import` depth, with cycles detected (ST24). Exhausting them harms only the attacker's own tab, but a stack overflow would abort the renderer, so recursion depth is bounded wherever input controls it (inference).
- **Cross-origin stylesheets:** a response that isn't `text/css` isn't applied (ST2), and ORB has already blocked cross-origin responses of other types in the network process (NW12); script can't read a cross-origin sheet's rules (ST30).
- **`:visited` without leaking history:** a renderer holds only the visited entries its own origin could have observed (ST10). A renderer never holds the global history, so a compromised one can't read it. The historical alternative, restricting styles and lying to `getComputedStyle`, is what Selectors 4 calls "an arms race that can't be won" (§9, alternative G).
- **No selector JIT:** renderer profiles keep `(deny dynamic-code-generation)` (J3, ST11).
- **Fonts and images referenced by CSS** go through text's and images' validation (TX7, TX8).
- **Exfiltration through CSS within a page,** such as attribute selectors that load URLs, is governed by Content Security Policy, staged with CP16 and CP17.

## 8. Staging and the complete model

| Stage | What exists |
|---|---|
| First document milestone | The tokenizer and parser; the property table for the properties the first layout uses; selectors without `:has()`; the cascade with origins, layers and `!important`; inheritance and custom properties; shared computed styles, the rule tree and the sharing cache; invalidation sets; media queries; `@import`; `@font-face` handed to text; the CSSOM's sheets and declarations; `getComputedStyle` |
| Next | Shadow DOM's scoping (`:host`, `::slotted()`, `::part()`); `@scope`; nesting; `:has()`; container queries with CP15 (and ST25's lifecycle); CSS animations and transitions on Web Animations; compositor animations for GR9's first set; constructed sheets; `@property`; partitioned `:visited`; `zoom` and `attr()` (Round 2, RV2-15) |
| Later | Scroll-driven animations and GR9's next set; view transitions (with CP15 and CP4); `@starting-style`; the CSS Typed OM; paint worklets; parallel style, if profiling asks for it |

**The complete model** (SC9): every CSS module fits these rules without architectural change. A new property is a row in ST3's table; a new selector or pseudo-class extends ST7's form and ST19's invalidation map; a new at-rule extends the parser and the contents' tree (ST30); a new query feature joins ST23's environment; new animatable properties join ST28's list when GR9's does. Parallel style stays possible behind ST33. **Four hooks named in Round 2** ([RV2-15](../review/round-2/03-findings.md#rv2-15-style-hooks-from-interop-2026)), each a change to a rule but not to the architecture, so the claim can be checked: the position fallback origin is a value of ST12's origin field; anchor positioning's fallbacks are ST25's nested lifecycle for one element, under IV1's amendment; effective zoom is an inherited factor in ST4's computed stage; `attr()` adds dependencies to ST19's invalidation from the declaration's side. **Staged:** `zoom` and `attr()` with the second stage (M4); anchor positioning with layout's, when a corpus page or a milestone's selection needs it.

## 9. Alternatives considered

| | Alternative | Assessment |
|---|---|---|
| A | **Stylo** as the style engine | Mature, fast and parallel, and in Rust. But DP1 (b) makes style core; it parses UTF-8 text, so every stylesheet and inline style would be converted from PL11's forms; its traversal sends nodes between threads with `unsafe`, and keeps element data behind `AtomicRefCell` (§3). Rejected; kept as precedent |
| B | **`cssparser` and `selectors`** alone, under Axiom's own cascade | Smaller, but the same UTF-8 conversion, and DP1 (a) makes parsing core. Rejected |
| C | **No rule tree,** only a cache keyed by a hash of what matched, as Blink and WebKit do | One cache fewer, but no shared identity for "what matched" to compare by pointer, and Blink's cache loses an entry when two results share a hash (§3). Axiom keeps both: the rule tree for identity, the cascade cache keyed by it (ST14, ST17) |
| D | **A selector JIT,** as WebKit has | Forbidden in renderers without `renderer-jit` (J3), and unnecessary on the evidence of the other engines. Rejected (ST11) |
| E | **Ladybird's engine design** as a whole: a dependency program over versioned inputs | The newest design, built around memory as Axiom's is. But it has been in production for two months, in one engine. Its two transferable principles are adopted (ST17, ST22, ST34); the design is revisited at the implementation milestone, with Ladybird's experience by then |
| F | **Parallel style from the start** | PL10: built only when profiling justifies it. ST33 keeps it possible |
| G | **`:visited` with restricted styles,** global history in every renderer | The historical approach. Selectors 4 records that hostile pages still extract history through it, and it would put the whole history in every renderer, where a compromised one could read it. Rejected for partitioning (ST10) |
