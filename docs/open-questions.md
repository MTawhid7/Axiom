| ID | Question | Why it matters | Evidence / input needed | Decide by | Status |

| OQ-1 | What is the time budget (hours per week) and horizon? | Sets how realistic the roadmap is, given the own-JS-engine and app-web scope | Owner input | Step 6 (roadmap) | **Resolved 2026-10-16:** no calendar deadline and no fixed hourly budget. Work is paced by bite-sized, self-contained checkpoints |
| OQ-2 | What is the target-site corpus? (Concrete URLs per tier, for example documents, content sites, interactive sites, apps) | Success criteria and milestone acceptance depend on it | Owner's list of sites they actually use | Step 6; ideally earlier | Open |
| OQ-3 | WebAssembly: write our own engine or embed one (for example Wasmtime with Cranelift)? | App-web reachability (Figma-class sites); size of the attack surface; schedule | JS engine design (Step 4–5); evaluation of embedding options | Before any Wasm milestone | Open |
| OQ-4 | JIT policy: if and when to add a baseline JIT, and when to disable JIT (sensitive sites)? | The JIT is the highest-risk attack surface; it determines performance on app-web sites | Isolation and sandbox design (Step 3); interpreter performance data | Step 3 (policy); much later (implementation) | Policy drafted in ADR-0001 |
| OQ-5 | Per-agent heaps: how are workers, `SharedArrayBuffer` and cross-agent messaging represented in the GC design? | Affects GC architecture and the process model | S1 results; Step 4 design | Step 4 | Open |
| OQ-6 | Which languages is the owner fluent in? | Learning cost is a factor in ADR-0002 | Owner input | Before ADR-0002 is accepted | **Resolved 2026-10-16:** the owner is fluent in Rust. Code must not be simplified for learning reasons |
| OQ-7 | When should full Xcode be installed (Instruments, Metal tooling)? | Serious profiling; Metal debugging | Owner preference | Before the first performance-critical milestone | Open. **S2 evidence (2026-10-17):** the Command Line Tools have no offline Metal compiler. Shaders compile from source at run time instead: about 0.5 s the first time, cached by macOS afterwards ([S2 results](research/s2-results.md) §3, §7). Profiling works without Xcode (samply) |
| OQ-8 | Version control: initialize a git repository for `docs/` now? | ADR history and diffs; continuity across sessions | Owner authorization | Now (recommended) | **Resolved 2026-10-16:** repository initialized; baseline `a223fe2` on `main`. Step 2b work is on branch `step-2b` |
| OQ-9 | Is the owner the only human developer? | Roadmap, review process, workload | Owner input | Step 6 | Assumed yes |
| OQ-10 | Which GC handle/rooting pattern: gc-arena-style, Nova-style scoped handles, or an unsafe core with a precise shadow stack? | Decides whether `unsafe` stays contained (the key ADR-0002 hypothesis) | Spike S1 | Before ADR-0002 is accepted | **S1 complete 2026-10-17.** Recommendation: Pattern B (Nova style), with five conditions ([S1 results](research/s1-results.md) §9). Decided in ADR-0003 at CP9 |
| OQ-11 | Platform shell: pure Rust (objc2) or a thin Swift layer? | Ergonomics against the cost of two toolchains | S2; Step 4 | Step 4 | **Leaning pure Rust, supported by S2 (2026-10-17):** objc2 handles the window, Metal and CoreText path with most calls safe and 19 `unsafe` sites, all contained ([S2 results](research/s2-results.md)). Accessibility, IME, menus and app bundles are untested |
| OQ-12 | What are the build-time and memory thresholds on the 8 GB M1? | Revisit condition 3 for ADR-0002 | `tools/measure-build.sh` (from CP1); S1 and S2 measurements | Thresholds set in CP8 (evaluation §15.6 assigns them to S2) | **Thresholds proposed:** T1–T4 in [S2 results](research/s2-results.md) §6, for the owner to decide at CP9. Today the S1 + S2 workspace builds clean in 8.1 s and incrementally in under 1 s; the largest `rustc` uses 0.35 GiB with trimmed bindings and 1.4 GiB with objc2's defaults |
| OQ-13 | Incremental or generational collection, and a write-barrier API, for the chosen GC pattern | S1's Pattern B pauses are stop-the-world: about 4 ms at 130k live nodes and 15 ms at 333k objects. Its plain field writes cannot support incremental marking (S1 conditions C3, C4) | ADR-0003; a pause budget (Step 6 performance section); a barrier prototype, with S1-Q2's ceremony recounted | Step 4, before the JS object model is fixed | Open (raised by S1) |
| OQ-14 | Root-stack design for Pattern B: can rooting cost at most 1 ns per root and per read? | Rooting dominates B's overhead in code that holds many handles across possible collections: dispatch takes 2.06× A's time. Measured unit costs are 2.05 ns per root and 1.58 ns per read (S1 condition C1) | A prototype measured with `s1-probe roots` and the dispatch suite; an interpreter-shaped benchmark | Step 4 | Open (raised by S1) |
| OQ-15 | Should S3, an interpreter micro-benchmark, become required rather than optional? | It would measure rooting traffic inside an interpreter loop, the main unmeasured input to ADR-0003 | Owner decision | CP9 | Open (raised by S1) |
